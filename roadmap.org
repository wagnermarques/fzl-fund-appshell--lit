* Visão geral

Este projeto é um *appshell* de referência: uma casca de aplicação (shell)
reutilizável, pronta para instalar como PWA, que serve de ponto de partida
para os demais projetos da família =fzlbpms-funds= (e, potencialmente,
outros produtos da FzlSoft). A ideia não é construir um framework próprio,
e sim fixar um conjunto pequeno e bem testado de decisões técnicas — stack,
estrutura de pastas, padrões de estado, camada opcional de backend, PWA e
deploy — para que iniciar um novo app deixe de ser "decidir tudo de novo" e
passe a ser "copiar o shell e trocar o domínio".

O nome do diretório (=fzl-fund-appshell--lit=) já marca duas decisões:
- é o appshell da linha "funds" da FzlSoft;
- é a variante construída em [[https://lit.dev][Lit]] — o sufixo =--lit= deixa margem para,
  no futuro, existir uma variante em outra stack sem colidir de nome.

** Projeto de referência

Como modelo de base tecnológica e de funcionalidades, usamos o projeto já
existente em =temp/biblereaderapp= (Bíblia PWA). Não é um projeto do mesmo
domínio de negócio, mas é exatamente o tipo de aplicação que este appshell
precisa suportar bem: PWA instalável, 100% funcional offline, com uma
camada de sincronização *opcional* contra um backend gerenciado. É um bom
modelo porque as decisões difíceis (offline-first, sync com fila,
autenticação opcional, tema, deploy) já foram tomadas e testadas ali — o
trabalho aqui é extrair o que é *genérico* e descartar o que é específico
do domínio bíblico.

* Por que esta stack

| Peça               | Escolha                          | Motivo                                                                 |
|---------------------+-----------------------------------+-------------------------------------------------------------------------|
| Componentes de UI  | Web Components nativos ([[https://lit.dev][Lit]])    | Sem vendor lock-in de framework; interoperável com qualquer host page  |
| Design system      | [[https://github.com/material-components/material-web][Material Web]] (Material 3)         | Componentes prontos e acessíveis, tema claro/escuro de fábrica          |
| Build              | [[https://vitejs.dev][Vite]]                              | Padrão de mercado, rápido, zero config para o caso comum                |
| PWA                | [[https://vite-pwa-org.netlify.app/][vite-plugin-pwa]] (Workbox)         | Manifest + service worker gerados, sem reinventar caching               |
| Roteamento         | Hash router artesanal (~50 linhas) | Funciona em GitHub Pages e qualquer host estático sem configurar rewrite |
| Estado local       | =localStorage= via *storage-service* | Offline-first real: o app funciona sem rede e sem conta desde o início  |
| Backend opcional   | [[https://supabase.com][Supabase]] (Postgres + Auth + RLS)  | Só entra em cena se as env vars existirem; sem elas, nada muda no app   |
| Deploy             | GitHub Actions → GitHub Pages     | Zero infra própria para o caso comum de app estático                   |

A escolha mais importante aqui não é nenhuma tecnologia isolada, é o
*padrão de camadas*: tudo funciona 100% sem backend, e o backend — quando
configurado — só sincroniza o que já existe localmente. Esse é o contrato
que queremos herdar para todo appshell derivado.

O que muda de projeto para projeto fica isolado: as *views* de domínio
(equivalente a =chapter-view.js=, =search-view.js= no biblereaderapp), o
schema de dados em =supabase/migrations/=, e o conteúdo de =public/data/=
(se existir). O shell em si — top bar, drawer, tema, roteador, PWA,
storage-service, auth/sync — deve ser praticamente copy-paste.

** app-shell.js — a casca

Do biblereaderapp herdamos o formato: uma =top-bar= fixa (menu, título,
ações rápidas, indicador de sync, toggle de tema) + um
=md-navigation-drawer-modal= com o menu organizado em seções via
=nav-accordion= + uma área =<main>= que troca de conteúdo conforme a rota.
Esse componente único concentra:
- o estado de UI (drawer aberto/fechado, tema, escala de fonte);
- a assinatura do roteador (troca a view renderizada);
- o registro do service worker e o toast de "nova versão disponível" —
  padrão importante para PWA instalável: o usuário decide quando recarregar,
  em vez de a versão ativa trocar sem aviso.

O menu do drawer é a parte mais óbvia de "template" — no biblereaderapp
tem seções como "Livros", "Bíblias", "Marcações"; no appshell genérico
ficam apenas os itens estruturais (Início, Sobre, Conta) e cada projeto
derivado acrescenta as seções do seu próprio domínio.

** Roteador

Hash router deliberadamente simples (sem dependência), porque:
- funciona em hospedagem 100% estática (GitHub Pages, S3, etc.) sem
  precisar configurar rewrite de servidor;
- é fácil de auditar e estender (o biblereaderapp tem uma nuance real
  documentada nele: distinguir a hash de rota da hash que o Supabase usa
  para devolver tokens de autenticação — =isAuthCallbackHash=). Isso é o
  tipo de armadilha que vale a pena já vir resolvida no shell.

** Tema e Material 3

Tema claro/escuro/sistema com tokens de cor centralizados em
=styles/theme.css=, e ícones do Material Symbols *autohospedados* (não via
Google Fonts) — decisão que vale a pena manter: mantém o catálogo de
ícones disponível offline e sem depender de domínio externo, essencial
para um app PWA instalável.

** storage-service — padrão local-first

O storage-service do biblereaderapp tem um padrão que vale generalizar
tal como está: uma pequena camada de =readJSON=/=writeJSON= sobre
=localStorage=, com helpers genéricos de lista com chave
(=toggleInList=, =mergeIntoList=, =isInList=) que qualquer domínio pode
reaproveitar (favoritos, itens lidos, marcações — no domínio de "funds"
seria, por exemplo, itens fixados, filtros salvos, rascunhos). O appshell
deve trazer só os helpers genéricos + as chaves estruturais (tema, escala
de fonte, fila de sync); as chaves de domínio (bookmarks, marked-texts)
não fazem parte do shell.

** Camada opcional de backend (auth + sync)

Este é o pedaço mais valioso a herdar, porque é o mais fácil de errar:
- =backend-client.js=: cria o client só se as env vars existirem;
  caso contrário exporta =null= e todo o resto do app trata isso como
  "modo 100% local, sem conta".
- =auth-service.js=: wrapper fino, síncrono para o usuário atual,
  observável via =subscribe()=.
- =sync-service.js=: fila *outbox* em =localStorage= (mudança é
  gravada local primeiro, sempre), com *debounce*, *flush* seqüencial
  que para no primeiro erro de transporte (preserva ordem), distinção
  entre erro de transporte (retry) e erro definitivo do servidor
  (marca como falho e não repete), e status observável
  (=synced/pending/syncing/offline/error=) para a UI mostrar um
  indicador de sincronização.
- Schema Postgres com *Row Level Security* desde a primeira migration,
  e criação automática do perfil via trigger em =auth.users=.

Esse conjunto (outbox + RLS + client condicional) é o "kit de sync
opcional" do appshell. Um projeto derivado que não precisa de conta
alguma simplesmente não copia =supabase/= nem os três services — o
resto do shell não depende deles.

** PWA / offline

=vite-plugin-pwa= com =registerType: 'prompt'= (nunca troca a versão em
uso sem avisar), precache do essencial da aplicação, e um padrão de
*runtime caching seletivo* para dados grandes — no biblereaderapp, só a
tradução padrão entra no precache (~4&nbsp;MB) e as demais são cacheadas sob
demanda no primeiro acesso. Esse padrão — "precache o mínimo necessário
para o app abrir, cache sob demanda o resto" — é o que evita instalar
PWA gigante em projetos com muito dado estático.

** Uso como submódulo git (pontos de extensão)

/Decisão de [2026-09-15 ter]: o appshell passa a ser consumido como
*submódulo git* pelos apps da família, não copiado. O primeiro consumidor
é o =legisreader= (=legisreader/appshell/=; lá, este trabalho é o marco
A1)./

Consequência: um app que usa o shell *não pode editar nenhum arquivo
dele*. Tudo o que hoje está fixo e é específico de um app precisa virar
configuração. Levantamento feito no commit =d4f13af=:

| Ponto fixo hoje                                        | Onde                                         | Problema para o app hospedeiro                         |
|--------------------------------------------------------+----------------------------------------------+--------------------------------------------------------|
| Rotas em =parseHash()=; rota desconhecida cai em =home= | =src/router.js=                               | O app não consegue criar rotas, nem rotas com parâmetros |
| =switch= em =_renderRoute()= e imports das views        | =app-shell.js=                               | O app não consegue renderizar as próprias views        |
| Seções "Conta" e "Config" do drawer                    | =app-shell.render()=                          | O app não consegue acrescentar, ordenar ou esconder seções |
| =<slot>= do =<app-header>=                              | Dentro do shadow DOM do =<app-shell>=, sem repasse | Inalcançável de fora; o slot existe, mas não serve    |
| Título "Fund Appshell"                                 | =app-header.js=, =home-view.js=, =index.html= | Nome errado no app                                     |
| Chaves =fzl-appshell:*=                                | =auth-service.js=, =notification-service.js=  | Apps em =wagnermarques.github.io/<repo>= compartilham a origem e, portanto, o =localStorage=: sessão e notificações vazariam entre apps |
| Leitura da sessão *no momento do import*               | =auth-service.js= (=let currentUser = loadCurrentUser()=) | Uma configuração passada em runtime chegaria tarde demais para o prefixo |
| Manifest, =define= de =__APP_VERSION__=, plugin PWA      | =vite.config.js= do shell                     | O Vite usa o config do *app*, e =virtual:pwa-register= quebra sem o plugin |
| Fonte com URL absoluta =/fonts/…woff2=                  | =theme.css= + =public/fonts/= do shell        | Quebra com =base: '/<repo>/'= e o =public/= usado é o do app |
| =generate-icons.mjs= com caminhos relativos ao shell    | =scripts/=                                   | Gera ícones dentro do submódulo, não no app            |
| =lit= / =@material/web= em =dependencies=                | =package.json=                               | Risco de *duas cópias* do Lit no bundle → =customElements.define= falha com "already been defined" |

*** API proposta: configuração declarativa única

Recomendação: o app descreve tudo num único objeto, no próprio =main.js=,
em vez de chamadas =registerX()= espalhadas. Fica explícito, é fácil de
validar e testar, e o próprio appshell passa a usar a mesma API como app
de demonstração.

#+begin_src js
// legisreader/src/main.js (ilustrativo)
import { createAppShell, pattern } from 'fzl-fund-appshell--lit'
import 'fzl-fund-appshell--lit/styles/theme.css'
import './webcomponents/norma-list-view.js'
import './webcomponents/dispositivo-view.js'
import './webcomponents/busca-campo.js'

createAppShell({
  mount: '#app',
  title: 'LegisReader',

  // Avaliadas em ordem, antes das rotas estruturais do shell.
  routes: [
    { name: 'busca', match: pattern('busca'),
      render: ({ query }) => html`<busca-view .query=${query}></busca-view>` },
    { name: 'dispositivo', match: pattern('br/*caminho'),
      render: ({ params, query }) => html`<dispositivo-view .caminho=${params.caminho} .query=${query}></dispositivo-view>` },
  ],
  home: () => html`<norma-list-view></norma-list-view>`,

  drawer: {
    sections: [
      { id: 'normas', label: 'Normas', icon: 'gavel', expanded: true,
        render: () => html`<norma-nav></norma-nav>` },           // conteúdo livre
      { id: 'estudo', label: 'Estudo', items: [
          { label: 'Favoritos', icon: 'bookmark', href: '#/estudo/favoritos' },
      ] },
    ],
    shellSections: { conta: true, config: false },              // seções do shell
  },

  headerActions: () => html`<busca-campo></busca-campo>`,
  footerItems: () => html``,
})
#+end_src

Detalhes:
- *Rotas*: =match(segments, query)= devolve =params= ou =null=. O helper
  =pattern()= cobre o caso comum (=:param=, =*resto=). A primeira rota que
  casar vence, e as rotas do app são testadas antes das do shell
  (=conta/*=, =config/*=). Uma rota inexistente mostra uma view "não
  encontrada", em vez de cair silenciosamente em =home=.
- *Navegação genérica*: =navigate(path, query?)= e =href(path, query?)=. Os
  =navigateToLogin()= / =navigateToAccount()= atuais continuam como atalhos
  das rotas estruturais do shell.
- *Drawer*: seção com =items= (lista simples) ou =render= (conteúdo livre,
  necessário para a árvore de uma norma). Um item pode ter =visible(user)=,
  porque "Conta" já depende do usuário logado.
- *Header e footer*: o =<app-shell>= renderiza =headerActions= e
  =footerItems= dentro dos =<slot>= que =<app-header>= e =<app-footer>= já
  expõem. Assim, esses slots passam a funcionar para quem está fora.
- *Validação*: =createAppShell= valida a configuração e falha cedo, com
  mensagem clara (rota sem =render=, =name= duplicado, seção sem =id=).

*** Configuração em tempo de build: prefixo de storage e versão

O =auth-service= lê a sessão *no momento do import*, e isso acontece antes
de qualquer =createAppShell()= rodar. Por isso, o que precisa existir desde
o import vem do *preset do Vite* como constante de build, igual ao
=__APP_VERSION__= atual:
- =__APP_STORAGE_PREFIX__=, com padrão igual ao =name= do =package.json= do app;
- =__APP_VERSION__=, agora lido do =package.json= *do app*, não do shell.

Um pequeno =storage-keys.js= (=storageKey('auth:session')= →
=legisreader:auth:session=) passa a ser usado por =auth-service= e
=notification-service=. É o embrião do M3.

*** Preset do Vite

#+begin_src js
// legisreader/vite.config.js (ilustrativo)
import { defineConfig, mergeConfig } from 'vite'
import { appshellConfig } from 'fzl-fund-appshell--lit/vite'

export default defineConfig(
  mergeConfig(
    appshellConfig({
      base: '/legisreader/',
      manifest: { name: 'LegisReader', short_name: 'LegisReader', theme_color: '#…' },
    }),
    { /* ajustes específicos do app, ex.: runtimeCaching dos dados */ },
  ),
)
#+end_src

O preset entrega: =VitePWA= com =registerType: 'prompt'= e
=injectRegister: null=, os =define= acima e =resolve.dedupe: ['lit',
'@material/web']=, como proteção extra contra cópias duplicadas.

*** Dependências e instalação: npm workspaces

- O app declara o submódulo como workspace:
  ="workspaces": ["appshell"]= no =package.json= do legisreader, com a
  dependência ="fzl-fund-appshell--lit": "*"=. O =npm install= roda *só na
  raiz do app*, e o npm cria um único =node_modules= compartilhado.
- O shell declara =lit=, =@material/web=, =@material-symbols/font-400=,
  =vite= e =vite-plugin-pwa= como =peerDependencies=, e as repete em
  =devDependencies= para continuar rodando sozinho (=npm run dev= dentro
  do próprio repositório).
- O =package.json= do shell ganha um campo =exports=: =.= (API),
  =./vite= (preset), =./styles/theme.css= e =./webcomponents/*= (para uso
  avulso de componentes).

*** Assets

- A fonte Material Symbols passa a ser importada por caminho relativo
  (dentro de =src/=, ou direto do pacote =@material-symbols/font-400=). O
  Vite inclui a fonte no bundle e aplica o =base= correto.
- =generate-icons.mjs= passa a receber =--svg= e =--out= (padrão: o
  diretório onde o comando é executado) e é exposto como =bin=
  (=npx appshell-generate-icons=).
- =index.html= e =public/= são sempre do app. O shell mantém os seus
  apenas para o modo de demonstração.

*** Compatibilidade

Ainda não há outro consumidor além do =legisreader=, então *mudanças
incompatíveis são aceitas agora* e não será mantida a API anterior. Depois
do A1, mudanças na API pública passam a exigir nota no commit e ajuste
coordenado nos apps que usam o shell.

* O que fica de fora do appshell (específico do domínio bíblico)

Para deixar claro o que é modelo e o que é domínio, isto *não* faz parte
do appshell genérico:
- =translations.js=, =bible-data-service.js=, =search-service.js= e as
  views de leitura/capítulo/busca — são o domínio do leitor de Bíblia;
- os dados em =public/data/<tradução>/=;
- as chaves de storage de domínio (=bookmarks=, =marked-texts=,
  =read-verses=) — o *padrão* (lista com chave, toggle, merge) fica; os
  dados em si, não;
- as tabelas =bookmarks=/=read_verses= da migration — ficam como
  *exemplo* de "como desenhar uma tabela com RLS a partir daqui", não
  como schema de produção do appshell.

* Convenções para projetos derivados

/Depois do A1, estes itens passam a ser feitos no próprio app (=base= e
=manifest= em =appshellConfig()=, ícones com =npx appshell-generate-icons=),
sem editar o shell./

- Trocar =REPO_NAME= em =vite.config.js= (usado no =base= do Vite e,
  possivelmente, no nome do repo do GitHub Pages).
- Trocar =manifest.name=/=short_name=/=theme_color=/=background_color= em
  =vite.config.js= e regenerar ícones com =scripts/generate-icons.mjs= a
  partir de um novo =public/favicon.svg=.
- Cada projeto derivado decide, independentemente, se usa a camada
  Supabase (copia =supabase/= + os três services) ou fica só local
  (não copia nada disso — o shell não deve ter esses arquivos como
  obrigatórios).
- Branch =main= como branch de trabalho e =production= como branch de
  deploy (ligada ao workflow do GitHub Pages) — convenção herdada do
  biblereaderapp, vale manter por padronizar o fluxo entre todos os apps
  da família.

* Licenciamento

O biblereaderapp usa AGPL-3.0 *especificamente* por causa do recurso de
sincronização em rede opcional (é a cláusula de uso em rede da AGPL que
faz diferença ali). Para um appshell interno da FzlSoft isso é uma
decisão em aberto, não herdada automaticamente — ver seção de decisões
pendentes abaixo.

* Decisões pendentes / riscos

- *=src/webcomponents/= hoje mistura dois tipos de componente*: os
  genéricos do shell (=app-shell.js=, =nav-accordion.js=,
  =md-imports.js=) e as views de domínio deste projeto específico
  (=home-view.js=, =config-rest-services-view.js=). Isolar tudo num só
  lugar foi o primeiro passo para permitir reaproveitar; o próximo,
  quando a reutilização entre projetos for de fato necessária, é
  separar os dois (ex.: =webcomponents/shell/= vs. =webcomponents/views/=,
  ou extrair só o primeiro grupo para um pacote próprio).
- *Supabase é o backend padrão da família, ou só do biblereaderapp?*
  Se a resposta for "cada projeto pode ter um backend diferente", vale a
  pena desenhar =backend-client.js=/=auth-service.js= atrás de uma
  interface pequena (signIn/signOut/subscribe/currentUser) em vez de já
  nomear tudo com "supabase" — troca de fornecedor não deveria implicar
  reescrever o app-shell.
- +*Modelo de distribuição do template*+ — *resolvido em [2026-09-15 ter]*:
  submódulo git + npm workspaces, com configuração declarativa (ver
  [[*Uso como submódulo git (pontos de extensão)][Uso como submódulo git]] e o marco A1). Copiar o template ou usar
  degit fica descartado, porque perderia a evolução independente do shell.
- *Submódulo exige disciplina*: o app fixa um commit do shell. Atualizar é
  um ato deliberado (=git submodule update --remote= + teste), e alterações
  feitas "de dentro" do app (=legisreader/appshell/=) precisam de commit e
  push no repositório do shell /antes/ do commit no app. Senão, o app
  aponta para um commit que não existe no GitHub e o CI quebra.
- *Licença*: decidir se este appshell (e os projetos derivados sem
  Supabase) precisam mesmo de AGPL, ou se — sendo software interno da
  FzlSoft, sem redistribuição pública — faz mais sentido uma licença
  proprietária/interna simples, reservando AGPL só para quando um
  projeto específico tiver o mesmo motivo do biblereaderapp (sync em
  rede opcional e distribuição pública).
- *Múltiplos frameworks de UI*: o sufixo =--lit= no nome do repo sugere
  que pode existir uma variante não-Lit no futuro. Vale confirmar se
  isso é intenção real antes de investir em abstrações "framework
  agnostic" prematuras no shell.

* Sugestões adicionais

Algumas idéias que não vieram do biblereaderapp, mas que valem
considerar para este ser de fato um bom ponto de partida repetível:

- *Testes desde o início*: o biblereaderapp de referência não tem
  suíte de testes; para um *template*, vale já nascer com
  [[https://vitest.dev][Vitest]] configurado (ao menos para o storage-service e o router, que
  são puros e fáceis de testar), para que cada projeto derivado herde o
  hábito em vez de adicionar depois.
- *Lint/format consistentes*: ESLint + Prettier (ou Biome) no shell,
  para que toda a família de apps tenha o mesmo estilo sem decisão
  repetida por projeto.
- *Tokens de marca separados do Material 3 default*: extrair as cores
  em =theme.css= como variáveis próprias por cima dos tokens
  =--md-sys-color-*=, para trocar a identidade visual de cada app sem
  reescrever o CSS inteiro — hoje o biblereaderapp usa a paleta padrão
  do Material.
- *Storybook (ou equivalente leve) para os componentes do shell*:
  como =app-shell.js= e =nav-accordion.js= vão se repetir em vários
  projetos, catalogar visualmente esses componentes ajuda a revisar
  mudanças no shell sem precisar rodar cada app derivado.
- *i18n desde o shell, mesmo com um só idioma hoje*: o biblereaderapp
  tem todo texto em português direto no template literal. Se algum
  projeto da família precisar de outro idioma no futuro, vale isolar as
  strings estruturais do shell (menu, botões de tema, toast de update)
  desde já, em vez de fazer essa extração depois com N projetos já
  copiados.
- *Verificação automática do checklist de "novo projeto"*: um script
  simples (=scripts/rename-project.mjs=?) que já troca =REPO_NAME=,
  nome do manifest e regenera ícones a partir de um novo favicon,
  reduz o checklist manual da seção acima a um comando.
